# 农场视觉升级最终验收设计

**日期：** 2026-08-03

**状态：** 设计已批准

**架构窗口：** ARCH-11

## 1. 目标

为已经完成的农场视觉升级建立一次独立、证据驱动、端到端的最终验收。验收覆盖农田、加工、订单、仓库、商店、Dashboard 首页库存和桌宠成熟作物提示，确认「明亮家园」视觉语言、响应式布局、无障碍、交互语义、回退链、动效治理、生命周期和打包态在同一最终提交上共同成立。

本阶段只做验证，不做实现。`farm-visual-08` 必须保持仓库只读；发现问题后保留最小复现并上报，由 ARCH-11 与用户决定是否创建精确的 `farm-fix-*` 窗口。

## 2. 已批准路线与备选方案

讨论过三种最终验收组织方式：

1. **证据驱动的端到端验收矩阵——已批准。** 按“界面 × 分辨率 × 状态 × 交互 × 生命周期”建立矩阵，同时使用自动测试、真实 Electron 操作、截图、尺寸测量、故障注入和同版 `app.asar` 证据。它最适合作为整体升级的最终签收。
2. 按农田、加工、订单、跨页面图标和桌宠提醒分别验收。问题定位直接，但对跨页面状态、缓存复用、生命周期和长时间往返覆盖较弱。
3. 复用历史窗口结论并只做抽查。成本最低，但缺少独立性，无法可靠发现集成后出现的回退、焦点、生命周期或打包问题。

最终采用方案 1，并把方案 2 作为验收矩阵内部的问题归类方式。历史窗口证据只用于理解基线，不能替代当前 HEAD 的新鲜验证。

## 3. 窗口职责与只读边界

`farm-visual-08` 是最终独立验收窗口，不承担实现或返修：

- 仓库全程只读，不修改生产代码、测试、素材、配置、文档或 Git 状态；
- 可以按锁文件安装依赖、运行测试、启动 Electron 和执行 Forge 打包，但不得修改 `package.json`、`package-lock.json` 或执行 `audit fix`；
- 只允许在 `/tmp/farm-visual-08-*` 创建临时探针、截图、日志和审计结果，交付前必须清理；
- 不改变农场经济、库存、事务、计时、提醒、宠物动作、回退链、持久化或业务 schema；
- 不复用实现窗口的“通过”结论，最终结论必须来自当前 HEAD 的新鲜证据；
- 发现问题后停止对相关验收项签收，不得在本窗口顺手修复；
- 仓库跟踪文档由 ARCH-11 在最终验收结束后统一更新。

运行测试、打包或依赖安装产生的 ignored 文件和构建目录不属于交付物。窗口必须在报告中区分它们与跟踪文件，并确保 `git status` 没有新增跟踪范围的修改。

## 4. 固定验收范围

### 4.1 人工与真实运行验收

人工验收覆盖：

- 农田主场景；
- 加工工坊；
- 订单板；
- 仓库；
- 商店；
- Dashboard 首页食物库存；
- 桌宠成熟作物提示。

每个适用界面覆盖：

- 800×600；
- 600×400；
- 正常资源路径；
- 已批准的回退路径；
- 正常动效与 `prefers-reduced-motion`；
- 页面隐藏、页签切换、页面往返和 cleanup；
- 源码态与同一最终 HEAD 的打包态。

### 4.2 自动回归范围

农场、Dashboard 和 pet 相关模块执行聚焦及相关回归；全仓执行 GUI 自动测试。与农场无关的页面不做逐页人工检查，但必须通过全仓自动回归。

### 4.3 明确不包含

- 修改或新增任何产品功能；
- 为审计便利改写生产代码或测试；
- 创建长期留存在仓库的截图、审计脚本或报告资产；
- 全应用范围的美术重审或 Emoji 清理；
- Godot、Unity、Spine、Rive 或其他技术路线迁移评估；
- 性能专项优化、依赖升级或安全审计修复。

## 5. 验收矩阵

### 5.1 视觉完整性

农田检查：

- 4×4 共 16 格土地完整可见，斜俯视网格、地块状态和土地等级清楚；
- 六种作物四阶段身份、锚点、占地和成长差异可辨；
- 洒水器、稻草人、堆肥箱及其等级、工作叠层和 fallback 表现正确；
- 奶油星团、小鸟、入口、选择轮廓和定位效果层级正确，不遮挡关键田块；
- 背景、独立地块、对象、角色、效果和交互层没有重复烘焙、异常穿透或错误排序。

加工检查：

- 机器英雄区、三槽生产轨道和五位配方架构图清楚；
- 齿轮、蒸汽、工作光和完成反馈没有漂移、裁切或遮挡；
- 五种配方、材料、产物和状态使用真实项目图标，文本不烘焙在图片中。

订单检查：

- 连续木质订单板和三张订单纸层级正确；
- ready、incomplete、cooldown、waiting 等适用状态不只依赖颜色区分；
- 数量、奖励、倒计时、按钮与纸张装饰没有重叠或裁切。

跨页面检查：

- 仓库、商店、Dashboard 首页食物库存使用项目物品图标；
- 桌宠成熟提示使用项目小麦图标与实时纯数字；
- 正常路径和项目 fallback 路径不输出物品 Emoji；
- 图片使用 `contain`，没有拉伸、裁切、透明 halo、断裂 alpha 或风格漂移。

### 5.2 响应式与无障碍

两档尺寸必须验证：

- 页面没有横向溢出；
- 宽屏侧栏和窄屏底部抽屉不覆盖农田关键交互区域；
- 窄屏加工与订单由页面根节点承担纵向滚动，不产生嵌套滚动陷阱；
- 原生按钮、disabled 状态、键盘顺序、焦点轮廓和 tooltip 保持；
- 16 格原生镜像继续保留可访问名称、`aria-pressed` 和键盘焦点；
- Canvas 选择、DOM 选择、详情面板和替换后的焦点节点保持同步；
- Dashboard 首页库存具有稳定的“名称，数量 N”无障碍标签；
- 图片进入最终隐藏状态后，名称、数量、价格、状态和操作仍然可理解；
- 焦点环不被容器裁切，状态不只依赖颜色或图片表达。

### 5.3 交互与业务语义

农田验证：

- 种植效果定位到目标格；
- 单格收获定位到目标格；
- 批量收获只在场景中心播放一次；
- 解锁和土地升级使用对应效果；
- 建筑建造、移动、升级和拆除在最终格播放建筑变化效果；
- 小鸟领取在小鸟位置播放金币反馈；
- Canvas 的 `select-tile`、`open-processing`、`open-orders`、`claim-bird`、`click-pet` 五类 intent 与 DOM/键盘路径一致；
- `click-pet` 只产生本地视觉反馈，不写 PetState/FarmService，也不改变闲置计时语义。

加工与订单验证：

- 加工入队、三批串行、running 不可取消、queued 取消确认与全额退款语义保持；
- 订单整单交付、放弃确认和 30 分钟冷却保持；
- 加工和订单成功反馈只在业务成功后出现，失败或取消不冒充成功；
- 倒计时、settlement gate、库存、金币、经验、奖励、提醒和事务顺序不变。

跨页面验证：

- 仓库使用、出售、销毁及右键入口保持；
- 商店购买、锁定提示、库存数量与右键购买保持；
- Dashboard 首页点击喂食、tooltip 和排序保持；
- 图标加载失败只影响表现，不改变交易、喂食或物品状态。

### 5.4 回退与异常

场景回退必须验证：

- 正常资源进入 Pixi；
- manifest、Pixi 初始化或关键资源失败时，在 trusted static 可用的情况下进入 static；
- static 不可用时交回现有完整 DOM；
- 单个作物、建筑、宠物、小鸟或其他 optional 资产失败时使用项目中性 fallback 或局部隐藏，不拖垮整个场景；
- 非法 manifest 路径不能发起越界或外部请求。

跨页面图片回退必须验证：

- 主图失败后只切换一次项目 fallback；
- fallback 再失败后图片进入 hidden 并移除无效 `src`；
- detached 节点、无关图片和 cleanup 后旧节点的错误被忽略；
- document 级错误监听器重复安装幂等，页面重绘不制造重复监听器。

异步异常必须验证：

- mount/update/loader/catalog 的迟到 resolve 或 reject 在 cleanup 后不复活 UI；
- 迟到失败被消费，不产生未处理拒绝；
- cleanup 异常不覆盖原始加载或初始化错误；
- 图片解码失败、静态回退和 DOM 回退不阻塞业务操作。

### 5.5 动效与生命周期

验证四类运行状态：

- 当前页签可见且允许动效；
- 页面隐藏；
- 离开农田进入加工或订单；
- `prefers-reduced-motion: reduce`。

对应合同：

- Pixi ticker、宠物、小鸟、局部对象循环和非必要效果在暂停条件下停止；
- 工坊齿轮与蒸汽 spritesheet 在隐藏或 reduced-motion 时停止；
- 恢复可见并允许动效后，只恢复必要实例，不重复创建场景或监听器；
- 一次性反馈不会被无限循环，也不会因快速重绘重复消费。

执行至少 20 次农田→加工→订单→农田，并穿插仓库、商店和 Dashboard 首页往返，验证：

- 单一 persistent scene host；
- 单一有效 Pixi Application/Canvas；
- document 图片错误监听器不重复；
- ResizeObserver、media listener、timer 和局部 ticker 数量受控；
- cleanup 后 Canvas、DOM 子节点、observer、listener、timer 和迟到异步均无残留。

### 5.6 自动化与发布态

按顺序执行：

1. manifest、scene model、layout、objects、adapter、loader、static、UI skin、processing、orders、跨页面 icon、pet reminder 等聚焦测试；
2. farm、Dashboard 和 pet 相关回归；
3. GUI 全仓 `node --test`；
4. 生产 JavaScript `node --check`；
5. `git diff --check`、范围扫描、禁业务写入和跨模块边界扫描；
6. `npm run package`；
7. 同一最终 HEAD 的 `app.asar` 内容和真实运行验收。

打包态必须从同一个 `app.asar` 内页面作为模块加载来源，不能使用 `about:blank` 跨来源模型代替真实应用。需要核实 Pixi distribution、farm manifest、运行时素材、21 个物品图标、项目 fallback、相关模块和 CSS 均进入 archive。

## 6. 证据合同

每个验收项必须记录：

- 验证对象与完整 commit；
- 源码态或打包态；
- Electron、Chromium、Node 版本；
- 窗口尺寸、DPR、Canvas CSS 尺寸和 backing 尺寸（适用时）；
- 操作步骤、预期结果和实际结果；
- `PASS`、`FAIL` 或 `ENVIRONMENT-BLOCKED`；
- 对应日志、测量值或 `/tmp` 截图路径。

证据要求：

- 只有当前 HEAD 的新鲜结果可以用于最终签收；
- 自动测试不能替代关键视觉和真实交互检查；
- 人工观察不能替代事务、竞态和生命周期测试；
- 旧包、旧截图或其他 worktree 的成功结果不能冒充最终 HEAD；
- 关键人工画面应包含 800×600、600×400、正常态、至少一个回退态和 reduced-motion；
- 截图、探针和日志仅存于 `/tmp/farm-visual-08-*`，交付报告提供索引，随后清理；
- 不向仓库提交大量验收产物。

## 7. 环境失败处理

沙箱、网络、GUI 权限或缓存问题必须与代码失败分开：

- 先记录失败命令、错误文本和环境；
- 用最小探针判断是产品路径还是执行环境；
- 若关键命令因沙箱、网络或 GUI 权限失败，按工具规则请求授权并在允许环境重跑；
- 不允许通过修改依赖、关闭测试或更换验证对象绕过环境问题；
- 环境恢复后必须在同一最终 HEAD 上重新取得新鲜结果。

如果关键验收项最终仍无法执行，总体结论不能是 `READY`。

## 8. 严重度与最终判定

### 8.1 问题等级

- **Critical：** 数据、事务、计时、生命周期、打包或主回退链损坏；关键页面不可用；发生状态写错、重复结算、资源泄漏或崩溃。
- **Important：** 主要视觉、交互、响应式、无障碍或已批准合同不成立；用户能稳定遇到明显错误，但不构成 Critical。
- **Minor：** 不影响核心使用的局部问题。若它违反已批准设计或验收合同，仍然阻断；只有不违反合同的纯美观建议可以作为后续优化。

### 8.2 最终结论

- `READY`：全部必要矩阵项具备新鲜证据，没有阻断问题；
- `READY WITH FOLLOW-UPS`：没有合同缺陷，只存在不阻断的纯美观建议，并由用户确认可后置；
- `NOT READY`：存在 Critical、Important、违反合同的 Minor，或关键验收项缺少可执行证据。

## 9. 问题路由

发现阻断问题后，`farm-visual-08` 必须：

1. 保留最小复现、日志、截图和影响范围；
2. 报告严重度、用户影响、疑似模块和建议修复文件；
3. 停止对相关项签收，不修改仓库；
4. 等待 ARCH-11 独立复核。

ARCH-11 复核后，必须先向用户报告推荐执行方、难度与理由、建议工具或技能、修复窗口编号、精确任务范围和允许修改文件。只有用户明确批准后才能创建独立 `farm-fix-*` 窗口。

## 10. 执行顺序

### 10.1 只读基线

- `git status --short --branch`；
- `git log --oneline --decorate -20`；
- `git diff --check`；
- 核对 HEAD、main、origin/main 和工作区；
- 确认被验收提交包含全部已批准农场视觉交付。

### 10.2 静态合同审计

核对资产路径、manifest、物品映射、CSS scope、模块边界、禁用业务写入、事件/IPC/依赖/持久化不变和打包资源入口。

### 10.3 自动测试

先聚焦、再相关回归、最后 GUI 全仓；随后执行语法、diff 和合规扫描。任何失败先做系统化根因分析，不能直接归因为环境或历史问题。

### 10.4 源码态真实验收

在两档尺寸下执行完整视觉、键盘、回退、动效、20 次往返和 cleanup 矩阵，并采集必要截图与测量。

### 10.5 最终 HEAD 打包

运行 Forge package，记录版本、耗时、产物位置和包体，检查 `app.asar` 内容。若环境阻塞，按第 7 节处理。

### 10.6 同版打包态验收

从最终 `app.asar` 内页面发起真实模块加载，复验 Pixi、跨页面图标、桌宠成熟提醒、五类 Canvas intent、三层场景回退、图片两级回退、两档布局和生命周期。

### 10.7 独立复核与报告

第二遍检查证据矩阵是否完整、是否误用旧结果、是否遗漏失败路径；清理 `/tmp/farm-visual-08-*`；输出测试计数、人工验证、打包态证据、竞态与生命周期、已知问题、临时文件清理和 Git 状态。

## 11. 完成条件

`farm-visual-08` 只有在以下条件全部满足后才可上报完成：

- 所有必要矩阵项均完成，不能以“此前窗口测过”代替；

如果存在阻断问题，窗口以 `NOT READY` 上报并等待修复路线；如果 `READY`，由 ARCH-11 更新 `PROJECT_BRIEF.md`、`docs/progress.md`、`docs/session-log.md` 并完成农场视觉升级阶段收尾。

## 12. 架构与长期路线

本验收不改变当前 Electron + PixiJS + DOM 的路线，也不新增事件、IPC、依赖、持久化或业务 schema。Godot 仍保留为长期可能路线，仅在未来需要更复杂场景、编辑器工作流或更高密度游戏内容时另行评估；本次最终验收不得借机推进技术迁移。
