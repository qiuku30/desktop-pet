# 农场经营系统设计

> 日期：2026-07-26
> 窗口：ARCH-10
> 状态：用户已逐节确认，待用户审阅书面版本

## 1. 目标与边界

首发交付一个可独立闭环、又能反哺宠物养成的轻度放置农场。核心由种植、邻接建筑、统一库存、加工和订单组成。

设计采用 A+C 混合：

- 种植区使用固定网格和邻接建筑，保留空间策略。
- 加工、订单和未来养殖使用独立经营区域，不占种植网格。
- 当前只有一块 `4×4` 基础农田；后续以新增带环境效果的农田扩展。

不在首发实现的能力见 `specs/farm-system.md`，但状态和配置不得阻塞这些扩展。

## 2. 架构方案

采用“纯规则引擎＋农场协调器＋页面层”。

### 2.1 纯规则引擎

职责：

- 时间戳生长和加工结算
- 邻接范围与同类最高等级选择
- 土地、建筑、心情和农田效果计算
- 订单生成与奖励估值
- 经验、等级和解锁判断
- 收获额外奖励
- 存档校验与迁移

要求：

- 不访问 DOM、IPC、PetState 或文件系统。
- 当前时间与随机源必须由调用方注入。
- 输入不可变，输出新状态或明确错误。
- 同一输入、时间和随机序列必须产生同一结果。

### 2.2 农场协调器

职责：

- 对外提供播种、收获、扩地、升级、建造、移动、拆除、加工、订单和小鸟领奖命令。
- 读取完整状态快照。
- 调用纯规则完成全部校验和计算。
- 通过 `PetState.setMany()` 原子提交农场、库存和经济字段。
- 成功提交后发出语义事件。

禁止页面直接拼接库存或奖励更新。

### 2.3 页面层

职责：

- 农田、加工、订单三个页签。
- 顶部跨页摘要。
- 事件绑定、生命周期清理和可访问交互。
- 根据协调器返回的稳定结果渲染反馈。

页面不实现收益公式、范围计算或时间结算。

## 3. 通用库存

引入通用库存：

```js
inventory = {
  [itemId]: count
}
```

稳定 ID 使用命名空间，例如 `seed:wheat`、`crop:wheat`、`food:cookie`。

物品配置独立描述名称、图标、分类、排序、出售能力、基础售价、投喂效果和解锁条件。配方独立引用物品 ID，因此新增配方无需修改原料物品类型。

旧 `foodInventory` 迁移要求：

1. 迁移函数识别旧数组并合入 `inventory`。
2. 重复运行不得重复增加数量。
3. 旧未知 ID 保留并记录警告，不能静默丢弃。
4. 现有喂食、商店和仓库改用库存门面。
5. 稳定 ID 永不复用；删除内容必须提供迁移映射。

## 4. 状态模型

建议概念结构：

```js
farm = {
  schemaVersion: 1,
  level: 1,
  exp: 0,
  activeFarmId: 'basic-farm',
  farms: {
    'basic-farm': {
      tiles: []
    }
  },
  processor: {
    level: 1,
    queue: []
  },
  orders: {
    slots: []
  },
  daily: {
    birdRewardDate: null,
    birdRewardCount: 0
  },
  notificationState: {
    notifiedReadyOrderIds: [],
    lastCompletedProcessingTaskId: null
  },
  nextIds: {
    order: 1,
    processingTask: 1,
    building: 1
  }
}
```

### 4.1 地图格

每个格子有固定坐标和稳定 ID，并且只处于 `locked`、`field` 或 `building` 中的一种占用状态。开放格始终保留底层土地等级；建筑只能占用无作物格，移走或拆除后恢复为原等级空田。

田地记录土地等级、当前作物、播种时间、成熟时间、本轮基础产量和修正快照，以及提供加成的建筑实例 ID。

建筑记录唯一实例 ID、类型、等级和累计投入金币。工作锁定由生长作物引用的建筑实例 ID 推导，不另存容易失真的布尔值。

### 4.2 加工任务

任务记录唯一任务 ID、配方 ID、输入和输出快照、入队时间、开始时间、完成时间和状态。第一项为运行中任务，其余为未开始任务。结算函数可以在一次调用中连续完成多批离线任务。

### 4.3 订单

每个槽保存订单 ID、需求快照、奖励快照、创建时间和放弃后的下次生成时间。订单创建后不随配置或市场变化，且没有截止时间。

订单需求从稳定排序的可行候选池中抽取。单项枚举所有价值落入等级预算区间的数量组合；双项要求两个不同物品、每项至少 1 且最多 20 个。Lv.4 起先按 70/30 选择单项或双项；双项池为空时降级为单项。排除其他槽的完整需求签名后仍无区间内候选时，确定性选择最接近区间下限且不重复的单项；完全无候选时保留空槽并在下次结算重试，禁止无界随机重试。

奖励快照固定为：

```js
{
  coins: 0,
  farmExp: 0,
  seedReward: null // 或 { itemId: 'seed:wheat', count: 1 }
}
```

金币和农场经验按需求创建时的材料直售价值计算。每单独立以 15% 概率附赠 1 粒种子；命中后从当前已解锁种子按稳定 ID 排序的候选中等概率选择。种子候选为空只令 `seedReward` 为 `null`。

### 4.4 实例 ID 与提醒去重

订单、加工任务和建筑使用持久化递增序号生成稳定 ID：`order:<n>`、`processing-task:<n>`、`building:<n>`。创建记录与递增 `nextIds` 必须属于同一事务；迁移按合法记录的最大序号向前修复，计数器永不回退。玩法随机源不得参与实例 ID 生成。

`notificationState.notifiedReadyOrderIds` 记录已经首次变为可交付的订单。第一次满足完整需求时与业务状态同事务写入，提交成功后才发 `farm:order:ready`；订单完成、放弃或替换后移除旧 ID。`lastCompletedProcessingTaskId` 记录最近一次队列全部完成时的末尾任务 ID，为后续聚合弱提醒提供跨重启去重键。

## 5. 配置模型

至少拆分：

- `ITEMS`
- `CROPS`
- `RECIPES`
- `BUILDINGS`
- `FARMS`
- `FARM_LEVELS`
- `LAND_UNLOCKS`
- `ORDER_CONFIG`
- `FARM_REWARD_CONFIG`

配置启动校验必须覆盖：

- ID 唯一且引用存在
- 时间、价格、产量和概率范围合法
- 等级条件可达
- 配方输入与输出合法且不存在无意循环
- 建筑范围和效果类型受支持
- 农田坐标唯一且初始开放格合法

进行中的种植、加工和订单使用创建时事务快照。配置调整只影响之后创建的任务。

所有首发默认数值、完整解锁表和经济参数以 `specs/farm-system.md` 第 4、5、7、8、9、11、12 节为准。实现不得在规则函数中复制这些值。

## 6. 事务与 PetState

新增共享接口：

```js
PetState.setMany(updates)
```

语义：

1. 校验 `updates` 为非空普通对象。
2. 先复制并替换全部目标字段。
3. 所有字段可见后，再按字段发送映射事件与 `PET_STATE_CHANGED`。
4. 一次调用只安排一次防抖保存。
5. 对象值继续执行防外部修改的复制规则。
6. 现有 `set()` 行为保持兼容。

农场事务流程：

```text
读取状态副本
→ 纯规则计算完整 next state
→ setMany 原子提交
→ 发出语义事件
```

典型原子事务包括快捷补购并播种、收获、订单提交、加工入队/取消、建筑拆除和小鸟奖励。

农场协调器串行执行所有命令，首发不保存额外 transaction ledger。已收获格清空、已完成订单替换、加工任务移出队列、小鸟状态清空并递增日计数等状态变化作为等价去重条件。

时间相关命令不得先独立提交 `settle()`。协调器先在内存中完成结算，再基于结算结果执行用户命令，最后最多调用一次 `setMany()`。提交后按“结算语义事件 → 用户命令事件 → 一次 `farm:state:changed`”发送。若用户命令失败但结算有变化，只提交结算结果并只发结算事件；结算和命令都无变化时不提交、不发状态事件。

`farm:state:changed` 的最小摘要由提交后的状态即时推导，不持久化：

```js
{
  farmLevel,
  farmExp,
  matureFieldCount,
  processing: {
    queuedCount,
    activeTaskId,
    nextCompletionAt
  },
  orders: {
    readyCount,
    coolingDownCount
  }
}
```

## 7. 时间与离线结算

不依赖后台逐秒运行：

- 生长保存 `plantedAt` 和 `readyAt`。
- 加工保存任务起止时间。
- 订单放弃保存 `regenerateAt`。
- 页面进入、应用启动、用户操作前以及低频 UI tick 时执行统一结算。
- 退出期间通过时间差补算。

需防御无效时间戳、系统时间回拨、跨本地自然日、超长离线、重复结算和页面销毁后的迟到回调。

小鸟每日上限按本地日期键计算，不使用 UTC 日期切片。

## 8. 农田与建筑计算

地图采用固定坐标。首发建筑范围：

- 1 级：曼哈顿距离 1，不含对角线。
- 2/3 级：切比雪夫距离 1，包含对角线。

同类型覆盖取最高等级，不相加；不同类型进入各自修正维度。

播种时计算并保存基础生长时长、农田环境、洒水器、宠物心情、基础产量、土地、稻草人、堆肥箱概率和贡献建筑实例 ID。

首发统一公式：

```text
实际时长
= 基础时长
÷ (1 + 洒水器加成)
÷ (1 + 心情加成)
÷ (1 + 农田环境加成)

最终产量
= round(基础产量 × 土地倍率 × (1 + 稻草人加成) × 农田环境倍率)
```

公式必须由单一纯函数实现，全项目不得重复计算。

## 9. 农场等级与解锁

农场经验来自收获和订单；加工、出售与投喂不提供农场经验。

内容通过独立 `unlockFarmLevel` 或宠物等级条件配置，不使用等级 `switch`。等级上限初始为 10，但从配置计算。

## 10. 页面结构

左侧导航新增“🌾 农场”。内部三个页签为农田、加工和订单。

顶部摘要在各页签持续存在，展示成熟田地数量、加工状态、可交付订单数量、农场等级和经验。

农场页面遵循现有 `_pageCleanup` 生命周期。切换页签可复用同一农场协调器，但必须清理页签专属 DOM 监听器。

## 11. 事件

正式事件：

- `farm:state:changed`
- `farm:crop:harvested`
- `farm:processing:completed`
- `farm:order:completed`
- `farm:order:ready`
- `farm:bird:rewarded`

旧占位事件 `game:farm:harvest` 和 `game:farm:food:synthesized` 在实现前移除，不保留双命名。

桌宠弱提醒消费农场摘要或语义事件，但不得改动既有宠物动作队列、闲置计时和 sleep 语义。

## 12. 容错

- 配置非法时只阻止农场模块挂载，显示错误占位。
- 存档按记录局部校验和修复，不因单个非法订单清空整个状态。
- 无法识别的记录隔离并记录警告。
- 所有奖励操作要求唯一事务 ID 或等价去重条件。
- 任何失败都不得产生负库存、负金币或半完成状态。
- 重复点击收获、订单和小鸟必须幂等或在首次提交后同步锁定。

schema v1 迁移采用逐记录局部修复：

- 未知格子删除，缺失标准格补回；非法占用在开放格恢复为空田、未开放格恢复锁定，土地等级裁剪到 1～3。
- 非法作物只清除该格作物；非法建筑实例删除，其占用格恢复为空田并保留合法土地等级。
- 单个非法加工任务删除；剩余任务保持顺序。运行任务被删除时，首个合法排队任务从迁移时刻开始，并依次重建后续时间。
- 单个非法订单槽改为空并令 `regenerateAt = now`；补足三个槽，但随机再生留给随后一次结算。
- `nextIds` 根据合法记录最大序号向前修复；提醒状态删除非法、重复和已不存在的订单 ID。
- 修复必须幂等，第二次迁移不得继续改变状态。

## 14. 实施拆分原则

农场横跨共享状态、面板、宠物和统一库存，必须使用 `farm-NN` 专属前缀拆窗。建议按依赖顺序实施：

1. 通用库存与 `PetState.setMany()`。
2. 农场纯规则、配置、迁移和协调器。
3. 农田页与建筑交互。
4. 加工和订单页。
5. 现有仓库、商店、喂食接入通用库存。
6. 桌宠弱提醒与最终集成验收。

具体窗口编号、执行方、文件权限和并行关系由 ARCH-10 在实施计划阶段提出，获得用户明确确认后才能创建。
